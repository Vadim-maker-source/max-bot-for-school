# Школьный MAX-бот

Заявка: описание → фотография → место → подтверждение. Черновики, заявки,
защита от повторных событий и очередь уведомлений хранятся в PostgreSQL.
Фотографии сохраняются в закрытую директорию, перед отправкой директору
проверяются и загружаются в MAX. Директор меняет статус или отклоняет заявку
с причиной; автор получает уведомление. Доступны «Назад» и «Отмена».

В проекте 12 исходных файлов:

```text
main.py             FastAPI, webhook, обработка очереди, запуск
bot.py              меню, FSM, заявки, действия директора
max_api.py          MAX API, TLS, фотографии, управление webhook
database.py         настройки, PostgreSQL, таблицы, миграция, обслуживание
Dockerfile
compose.yaml
Caddyfile
requirements.txt
.env.example
.gitignore
README.md
deploy.sh
```

Локальные `.env`, `.venv`, `private/` и `work/` содержат конфигурацию, окружение
и данные; они исключены из Git. Старой структуры `app/` и отдельного worker нет.

## Локальный запуск

Нужны Python 3.12+ и PostgreSQL 18. Создайте окружение, установите
`pip install -r requirements.txt`, скопируйте `.env.example` в `.env` и заполните:

- `MAX_BOT_TOKEN`, `MAX_TOKEN_CONFIRMED=true` — существующий токен;
- `POSTGRES_*` — отдельная роль без прав суперпользователя и принадлежащая ей БД;
- `WEBHOOK_SECRET` — случайные 32–256 латинских букв, цифр, `_` и `-`;
- `WEBHOOK_URL=https://домен/webhook` — публичный HTTPS-адрес.

Для новой локальной БД `python database.py init-db` запросит пароль администратора
без отображения, создаст роль и сохранит новый пароль в `.env`. Команда отказывается
менять существующие БД и роли. Для существующей БД оставьте текущие настройки.

```bash
python main.py
```

По умолчанию адрес `http://127.0.0.1:8010`. `/health` проверяет процесс,
`/ready` — БД, ревизию и включенный токен. При запуске применяются известные миграции.
Ревизия `0002_director_viewed` добавляет к `0001_initial` только nullable-поле
`repairs.director_viewed_at`, сохраняя прежние данные и статусы. Исторические заявки
остаются непросмотренными до открытия или изменения статуса директором.
Неизвестная ревизия или таблицы без истории останавливают запуск без изменения схемы.
Отдельное применение: `python database.py migrate`.

Если системе недостает доверенного сертификата MAX, выполните `python max_api.py ca`.
Команда скачивает CA с официального сайта по проверенному HTTPS, проверяет сертификаты,
создает частный bundle и записывает `MAX_CA_BUNDLE` в `.env`. TLS остается включенным.

Для временного HTTPS запустите установленный cloudflared: `python max_api.py tunnel`.
После смены временного адреса обновите webhook:

```bash
python max_api.py subscriptions
python max_api.py register --url https://домен/webhook --confirm
```

Сначала просмотрите подписки. Регистрация откажется заменять другой URL.
Удаление только текущего `WEBHOOK_URL`: `python max_api.py unregister --confirm`.
Токены и webhook-секрет берутся из `.env`, не передавайте их аргументами команд.

## Директор

Директор отправляет `/start` и `/id` в личном диалоге. Запишите его реальный
`user_id` и `DIRECTOR_CHAT_ID`, затем проверьте:

```bash
python database.py director --user-id 123456789
```

Сохранение проверенного пользователя и включение реальных отправок:

```bash
python database.py director --user-id 123456789 --enable-delivery --confirm
```

Перезапустите приложение. Включение доставки отправит также накопленные карточки.
До этого `DIRECTOR_DELIVERY_ENABLED=false`: карточки остаются в очереди.
Доступ проверяется по `DIRECTOR_USER_ID`, доставка — дополнительно по подтвержденному
личному диалогу. Идентификатор чата не заменяет идентификатор пользователя.

После `/start` директор видит «📥 Новые заявки (N)», «📅 Архив заявок» и кнопку
создания заявки. N — число непросмотренных заявок независимо от их статуса.
Уведомление не отмечает заявку просмотренной; это происходит при нажатии «Открыть»
или изменении статуса. В архиве выберите год (с 2026 до текущего года по Москве)
и месяц: бот покажет сводку статусов и список по 10 заявок, начиная с новых.
«Открыть №ID» выводит общую карточку с фото и существующими действиями директора.
После смены статуса нажмите «🔄 Обновить», чтобы получить актуальную сводку.
Границы месяца рассчитываются в Europe/Moscow, списки и годы имеют пагинацию.

## Docker и Caddy

Нужны Docker с Compose и свободные порты 72/TCP, 443/TCP, 443/UDP.
Приложение доступно по HTTP на порту 72, а webhook MAX принимает события по HTTPS
на порту 443. MAX не поддерживает webhook на порту 72.
Заполните `.env`, в том числе `PUBLIC_DOMAIN=94.232.42.94`,
`WEBHOOK_URL=https://94.232.42.94/webhook`, `POSTGRES_USER`, `POSTGRES_PASSWORD`
и отдельный `POSTGRES_ADMIN_PASSWORD`. Пароль администратора не передается приложению.
Ограничьте доступ к файлу: `chmod 600 .env`.

```bash
docker compose config --quiet
docker compose up -d --build
docker compose logs --tail=50 app
docker compose exec app python max_api.py register --confirm
```

Compose содержит PostgreSQL, приложение с обработчиком очереди и Caddy с HTTPS.
Домен необязателен: Caddy получает сертификат Let’s Encrypt для публичного IP
с профилем shortlived и продлевает его автоматически. Данные сертификатов должны
сохраняться в volume. Проверка владения адресом проходит через TLS-ALPN на 443;
порт 80 не используется. Если вместо IP указан домен, направьте его A-запись на сервер.
Порт БД наружу не публикуется. Роль приложения не имеет административных прав.
Dockerfile копирует только код и зависимости; секреты передаются при запуске.

Volumes `postgres_data`, `photos`, `caddy_data`, `caddy_config` сохраняют БД,
фотографии и состояние HTTPS при обновлении контейнеров. Не используйте
`docker compose down -v` для обычной остановки. Пароли в `.env` не меняют автоматически
учетные данные уже инициализированного PostgreSQL volume.

Локальная БД не переносится в Docker автоматически. Перед переносом остановите
локальное приложение, сделайте резервную копию, восстановите dump через
`pg_restore --no-owner --role=<роль приложения>` в отдельную пустую БД. Перенесите
содержимое директории фотографий в volume `photos`, с владельцем UID/GID 10001.
Проверьте данные и `/ready` до переключения webhook.

## Обслуживание и обновление

```bash
python database.py doctor
python database.py queues
python database.py backup
python database.py audit
```

Локальная резервная копия БД и фотографий: `private/backups/<UTC>/`.
Нужен `pg_dump` в PATH либо стандартная установка PostgreSQL 18 Windows.
Храните копии отдельно от сервера с ограниченным доступом. В контейнере используйте
`docker compose exec -T db pg_dump ...`: в образе приложения клиент PostgreSQL не установлен.

Повтор конкретного задания после устранения причины сбоя:
`python database.py queues --retry-inbox 123` либо `--retry-outbox 123`.
Явная очистка неиспользуемых фотографий старше семи дней:
`python database.py queues --cleanup-unused-photos`.
Заявки, черновики и ожидающие уведомления защищают связанные фотографии от очистки.
Само обновление данные не очищает.

Для Linux-сервера с чистым Git checkout и настроенным upstream:

```bash
bash deploy.sh
```

Скрипт проверяет конфигурацию, получает fast-forward обновление, собирает образ,
останавливает приложение, сохраняет БД и фотографии, применяет миграцию и проверяет
готовность нового контейнера. PostgreSQL, Caddy и volumes не пересоздаются.
Параллельные обновления блокирует `flock`. При сбое после начала миграции проверьте
причину и копию в `private/backups/`; автоматического отката БД нет.

Webhook сохраняет событие до ответа HTTP 200. Повтор события не создает вторую заявку;
заявка, статус и постановка уведомлений фиксируются транзакционно. Отправка сообщений
и подтверждения кнопок обрабатываются независимо от входящих событий внутри того же
процесса: загрузка фото не удерживает подтверждения кнопок. Очереди остаются в PostgreSQL,
порядок обычных сообщений и ограничение частоты отправки в один диалог сохраняются.
Общая частота запросов к MAX ограничена 30 в секунду на процесс. Отправка
повторяется с задержкой. Если соединение оборвалось после принятия сообщения MAX,
но до фиксации результата в БД, повторное уведомление возможно.
